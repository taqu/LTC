# Phase 5 — Reference Comparison and Numerical Validation

## Project: LTC LUT Generator

### Objective

Implement a comprehensive numerical validation framework for LTC LUTs generated by the previous phases.

The primary goals are to:

1. Verify generated GGX LTC coefficients against authoritative reference data.
2. Quantify the approximation error between the original GGX BRDF and the LTC representation.
3. Validate the reconstructed LTC distributions after DDS packing and FP16 quantization.
4. Implement independent CPU-based reference integration for area lights.
5. Evaluate polygonal area lights using LTC-based analytical integration.
6. Compare LTC area-light results against independent numerical ground truth.
7. Detect regressions, numerical instability, and incorrect LUT conventions.
8. Produce reproducible, machine-readable validation reports.

The implementation must remain CPU-only and independent of Unreal Engine.

Primary reference:

https://github.com/selfshadow/ltc_code

Relevant reference materials:

- `fit/fitLTC.cpp`
- `fit/LTC.h`
- `webgl/`
- *Real-Time Polygonal-Light Shading with Linearly Transformed Cosines*
- *Real-Time Area Lighting: a Journey From Research to Production*

**Phase 5 is a validation and correctness phase. Do not implement new BRDF models, new fitting optimizers, or GPU rendering functionality.**

Validate:

- Matrix coefficient conventions.
- Amplitude coefficients.
- Reference-specific texture packing.
- Numerical values of selected LUT cells.

### Unreal Profile

Purpose:

Verify compatibility with the specific Unreal Engine implementation targeted by the project.

Validate:

- DDS dimensions and formats.
- Matrix channel ordering.
- Amplitude semantics.
- Texture coordinate mapping.
- Bilinear interpolation.
- Reconstructed LTC coefficients.

The Unreal profile must require a documented target engine version and verified shader conventions.

Do not assume that selfshadow reference data and Unreal Engine data are interchangeable.

### Quality Profile

Purpose:

Evaluate numerical accuracy independently of implementation-specific reference coefficients.

Validate:

- BRDF approximation quality.
- LTC normalization.
- Interpolation stability.
- FP16 quantization effects.
- Area-light integration accuracy.

This is the main profile for assessing the actual quality of generated LUTs.

## 5. Reference LUT Comparison

Implement comparison of generated LTC textures against existing reference textures.

### Supported Inputs

At minimum:

```text
GGX_LTCMat.dds
GGX_LTCAmp.dds
```

Support comparison between:

- Two DDS texture pairs.
- Full-precision LUT data and decoded DDS textures, using an explicitly selected packing profile.
- Generated DDS textures and Unreal Engine reference DDS textures.

### Reference Compatibility Checks

Before comparing pixel values:

1. Inspect dimensions.
2. Inspect pixel formats.
3. Confirm channel counts.
4. Confirm coordinate mappings.
5. Confirm matrix packing conventions.
6. Confirm amplitude semantics.
7. Confirm reference version or provenance when available.

Reject incompatible comparisons unless an explicit, validated conversion exists.

Do not silently transpose matrices, swap channels, or reinterpret amplitude values to minimize errors.

### Metrics

For every comparable channel, calculate:

- Minimum and maximum values.
- Mean absolute error.
- Maximum absolute error.
- Root mean squared error.
- Mean relative error.
- Maximum relative error.
- Number of values exceeding configured thresholds.
- Coordinates of the largest discrepancies.
- Number of NaN and infinity values.

Use double precision for error accumulation.

Relative error must use a documented denominator floor.

### Region-Based Analysis

Report errors separately for:

- Low roughness.
- Medium roughness.
- High roughness.
- Normal incidence.
- Intermediate view angles.
- Grazing angles.

Use explicit, configurable region boundaries.

Do not rely exclusively on aggregate RMSE, since a small number of problematic cells may be hidden by the global average.

### Reference Data Policy

Do not fabricate golden values.

If authoritative Unreal Engine assets are unavailable:

- Run comparisons against available selfshadow reference data.
- Run internal numerical validation.
- Mark Unreal coefficient compatibility as unverified.
- Do not block unrelated validation functionality.

Reference assets must remain optional for normal CI.

## 6. LTC Distribution Validation

Validate the mathematical quality of the generated LTC distributions.

### 6.1 BRDF and LTC Functions

For the target BRDF:

\[
f_B(V,L)=f_r(V,L)\max(0,N\cdot L)
\]

For the LTC approximation:

\[
f_L(L)=A D_{\mathrm{LTC}}(L;M)
\]

where:

- \(A\) is the fitted magnitude.
- \(D_{\mathrm{LTC}}\) is the normalized LTC distribution.
- \(M\) is the fitted transformation matrix.

### 6.2 Error Metrics

Calculate several complementary metrics.

#### Absolute L1 Error

\[
E_1=\int_{S^2}|f_B(L)-f_L(L)|\,d\omega
\]

#### Squared L2 Error

\[
E_2=\int_{S^2}(f_B(L)-f_L(L))^2\,d\omega
\]

#### Cubic Fitting Error

\[
E_3=\int_{S^2}|f_B(L)-f_L(L)|^3\,d\omega
\]

#### Integrated Energy Error

\[
E_A=
\left|
\int_{S^2}f_B(L)\,d\omega-
\int_{S^2}f_L(L)\,d\omega
\right|
\]

The target BRDF must evaluate to zero outside its valid hemisphere.

Do not assume the transformed LTC is restricted to that same hemisphere.

### Independent Evaluation

Use a validation sampling pattern independent of the optimization sample grid.

Support deterministic stratified or low-discrepancy sampling.

Do not reuse exactly the same 32×32 midpoint samples and call the result independent validation.

Use higher sample counts for difficult low-roughness and grazing-angle cases.

### Directional Diagnostics

Evaluate errors over representative incoming directions.

Record:

- Largest local discrepancy.
- Direction of maximum error.
- Relative error where meaningful.
- Signed energy difference.

Do not clamp negative differences before computing diagnostics.

## 7. DDS Reconstruction Validation

The output of Phase 4 is quantized to FP16.

Validate the effective LTC representation obtained from the serialized DDS files.

### Required Procedure

1. Load the generated matrix DDS.
2. Load the generated amplitude DDS.
3. Decode FP16 pixel data.
4. Reconstruct the normalized inverse LTC matrix.
5. Reconstruct a representative forward matrix.
6. Recover the amplitude terms according to the selected profile.
7. Evaluate the reconstructed LTC distribution.
8. Compare it against the full-precision LUT distribution.

### Matrix Scale Invariance

LTC directional distributions are invariant under positive uniform scaling of the transformation matrix.

Therefore, compare distributions using a consistent matrix normalization.

Do not treat arbitrary overall matrix scale differences as shape errors.

### Quantization Metrics

Measure:

- Maximum matrix coefficient error.
- Mean matrix coefficient error.
- Reconstructed distribution error.
- Amplitude coefficient error.
- Invalid or near-singular reconstructed matrices.
- Cells with disproportionately large quantization effects.

Test low-roughness and grazing-angle cells explicitly.

### Bilinear Interpolation

Implement CPU-side bilinear LUT sampling that reproduces the selected runtime texture-coordinate convention.

For a conventional 64×64 LTC LUT:

\[
u=\frac{1}{2W}
+\frac{W-1}{W}r
\]

\[
v=\frac{1}{2H}
+\frac{H-1}{H}\sqrt{1-N\cdot V}
\]

The exact mapping must be overridden when the verified Unreal shader uses different conventions.

Implement:

- Texel-center mapping.
- Clamped addressing.
- Bilinear interpolation.
- Correct channel interpolation.
- Matrix reconstruction after coefficient interpolation.

Do not interpolate full matrices and normalize them afterward unless that is the actual target runtime convention.

### Interpolation Tests

Test:

- Exact texel centers.
- Cell boundaries.
- Roughness endpoints.
- View-angle endpoints.
- Interior UV coordinates.
- Non-square LUTs where supported.
- FP16 and FP32 inputs.

Use synthetic textures with analytically predictable interpolation results.

## 9. Independent Ground-Truth Integration

Implement a CPU numerical integrator that evaluates direct illumination from the original BRDF.

This integrator must not use LTC fitting coefficients.

### 9.1 Rendering Integral

For a polygonal emitter \(P\), evaluate:

\[
L_o(V)=
\int_{\Omega_P}
L_e(L)
f_r(V,L)
\max(0,N\cdot L)
\,d\omega_L
\]

Here, \(\Omega_P\) is the solid angle subtended by the emitting polygon, respecting its emission-sidedness.

For area-domain integration:

\[
L_o(V)=
\int_P
L_e(X)
f_r(V,L)
\frac{
\max(0,N\cdot L)
\,c_e(X,L)
}{
\|X-P_s\|^2
}
\,dA
\]

where:

- \(P_s\) is the shading position.
- \(X\) is the sampled point on the emitter.
- \(L=(X-P_s)/\|X-P_s\|\).
- \(c_e=\max(0,N_e\cdot(-L))\) for a one-sided emitter.
- \(c_e=|N_e\cdot L|\) for a two-sided emitter.

The BRDF evaluation must use the existing Phase 1 mathematical implementation.

### 9.2 Numerical Integration

Support deterministic high-sample-count integration.

Possible methods include:

- Stratified area sampling.
- Low-discrepancy area sampling.
- Adaptive subdivision.
- Triangle-based integration for convex polygons.

Use well-defined sample weights and PDF normalization.

### 9.3 Convergence Validation

Evaluate selected scenes at increasing sample counts, for example:

```text
4,096
16,384
65,536
262,144
```

These values are suggested test levels, not mandatory universal defaults.

For difficult cases, permit substantially higher sample counts.

Report convergence behavior.

Do not treat the highest-sample result as automatically exact.

Provide an uncertainty or convergence estimate, and use independent sampling sequences or numerical methods when practical.

### 9.4 Ground-Truth Independence

Ground truth must not:

- Use LTC coefficients.
- Use the LTC polygon integrator.
- Share a hidden approximation with the LTC result.
- Apply postprocessing or tone mapping.

Keep the validation in linear radiometric units.

For GGX, the target must match the exact Fresnel and geometry conventions selected for the fitted LUT.

## 10. LTC Polygon Integration

Implement an independent CPU evaluator for the analytical LTC polygon integration.

The method should follow the reference LTC area-light evaluation algorithm.

### 10.1 Transformation

For the shading point:

1. Construct the local surface/view coordinate frame.
2. Transform polygon vertices into the local frame.
3. Apply the inverse LTC transformation.
4. Normalize transformed directions.
5. Integrate the transformed spherical polygon against the cosine distribution.
6. Apply the appropriate LTC magnitude and emitted radiance.

Maintain consistency with the matrix convention established in Phases 1 and 4.

### 10.2 Polygon Integration

Implement the spherical polygon edge integration needed for LTC evaluation.

Handle:

- Correct edge ordering.
- Solid-angle integration.
- Orientation signs.
- Near-collinear edges.
- Very small angular separations.
- Horizon intersections.
- Completely clipped polygons.

Use double precision for intermediate calculations.

### 10.3 Horizon Clipping

Handle the cosine distribution's upper-hemisphere support.

For validation purposes, prefer geometrically correct horizon clipping rather than silently replacing it with a production-oriented approximation.

If the reference runtime uses an approximate clipped-sphere form factor, implement it as a separate optional evaluation mode.

Do not mix exact and approximate integration results in the same metric without labeling them.

### 10.4 Integration Modes

Provide distinct modes:

```text
exact-polygon
reference-runtime
```

`exact-polygon` should use a mathematically accurate polygon clipping and cosine integration procedure.

`reference-runtime` should reproduce the selected, verified shader convention, including any approximations.

If the exact runtime implementation is unavailable, report that mode as unsupported rather than inventing a substitute.

### 10.5 Baseline Validation

Validate the polygon integrator independently of GGX fitting.

Use the identity LTC:

\[
M=I
\]

with unit magnitude.

This reduces the test to integration of the normalized clamped-cosine distribution.

For simple polygon configurations, compare against independently computed numerical integrals.

Also test transformed LTCs with known valid matrices.

**Do not proceed directly to GGX lighting comparisons without first validating the LTC polygon integrator itself.**

## 11. Lighting Accuracy Validation

Compare the analytical LTC lighting result against the independent BRDF ground truth.

### 11.1 Error Metrics

For reference radiance \(L_{\mathrm{ref}}\) and LTC radiance \(L_{\mathrm{LTC}}\):

#### Absolute Error

\[
E_{\mathrm{abs}}=
|L_{\mathrm{LTC}}-L_{\mathrm{ref}}|
\]

#### Relative Error

\[
E_{\mathrm{rel}}=
\frac{|L_{\mathrm{LTC}}-L_{\mathrm{ref}}|}
{\max(|L_{\mathrm{ref}}|,\epsilon)}
\]

#### Signed Error

\[
E_{\mathrm{signed}}=
L_{\mathrm{LTC}}-L_{\mathrm{ref}}
\]

For RGB radiance, calculate per-channel errors and an explicitly defined aggregate metric.

Use a configurable relative-error floor.

Report absolute error separately for nearly black cases.

### 11.2 Test Dimensions

Vary:

- GGX roughness.
- View angle.
- Light size.
- Light distance.
- Light orientation.
- Light position.
- Emission sidedness.
- Polygon shape.

Include both common and difficult lighting conditions.

### 11.3 Required Test Cases

At minimum:

| Test | Purpose |
|---|---|
| Large frontal rectangle | Basic lighting accuracy |
| Small frontal rectangle | Narrow solid-angle illumination |
| Tilted rectangle | Orientation correctness |
| Grazing rectangle | High-angle stability |
| Partial horizon crossing | Clipping correctness |
| Fully below horizon | Zero-contribution behavior |
| Near-normal view | Normal-incidence behavior |
| Grazing view | Low NdotV behavior |
| Low roughness | Sharp highlight accuracy |
| High roughness | Broad-lobe accuracy |
| Convex polygon | General polygon integration |
| Rotated geometry | Coordinate invariance |

Include at least one nonzero-Fresnel material configuration if the selected profile supports Schlick Fresnel reconstruction.

Use the identical BRDF and Fresnel conventions for both LTC and ground truth.

### 11.4 Error Attribution

Separate the error into stages.

#### A. BRDF Approximation Error

Compare:

- Ground-truth BRDF integration.
- Full-precision LTC integrated with independent high-accuracy numerical integration.

This measures approximation quality without involving DDS quantization or analytical polygon evaluation.

#### B. Analytical Integration Error

Compare:

- Independently numerically integrated full-precision LTC.
- Analytically integrated full-precision LTC.

This isolates polygon integration and clipping errors.

#### C. LUT Interpolation Error

Compare:

- Full-precision LTC coefficients at the exact requested parameters, obtained from a separate single-point fit.
- Interpolated full-precision LUT coefficients.

Use a consistent fitting configuration and report the comparison's numerical limitations.

#### D. DDS Quantization Error

Compare:

- Interpolated full-precision LUT.
- Interpolated FP16 DDS reconstruction.

#### E. Total Lighting Error

Compare:

- Original BRDF numerical ground truth.
- Final DDS-based analytical LTC evaluation.

These separate comparisons are essential for diagnosing discrepancies.

Do not assume errors from individual stages combine additively.

## 15. Numerical Reliability

Numerical validation must not become a source of misleading results.

### Required Practices

- Use double-precision accumulation.
- Avoid uncontrolled summation-order differences.
- Detect NaN and infinity.
- Use explicit coordinate conventions.
- Validate sampling PDFs.
- Check area-sampling Jacobians.
- Track numerical integration convergence.
- Use independent validation samples.
- Distinguish error from reference uncertainty.
- Avoid arbitrary clamping of signed intermediate quantities.

### Ground-Truth Uncertainty

If the estimated numerical integration uncertainty is comparable to the measured LTC error, mark the result as inconclusive.

Do not report a strong accuracy claim when the reference integral has not converged sufficiently.

Permit higher-precision or higher-sample-count reruns for difficult scenarios.

### Threshold Policy

Do not invent universal accuracy thresholds before establishing a baseline.

Introduce configurable thresholds for:

- Coefficient RMSE.
- Matrix reconstruction error.
- Distribution error.
- Lighting absolute error.
- Lighting relative error.
- Allowed invalid cell count.

Initial thresholds should be based on independently verified reference results and documented numerical behavior.

Separate strict correctness checks from quality metrics.

A mathematically valid LTC fit may still have substantial approximation error for certain lighting configurations.

## 17. Performance

Phase 5 prioritizes correctness over speed.

However, the validation framework should support efficient CPU execution.

### Requirements

- Avoid unnecessary allocations in sampling loops.
- Cache invariant light geometry where appropriate.
- Avoid repeated DDS decoding for every sample.
- Avoid logging inside numerical integration loops.
- Support configurable sample counts.
- Report validation durations.
- Permit parallel execution of independent scenarios.

Parallel validation must not introduce nondeterministic sample sequences.

For deterministic reports, preserve stable output ordering.

Do not implement GPU acceleration.
